03 · Dell / Serviceability ~1 min 35 sec

04 · Log bundles: portable sidecars and parallel collection

A log bundle could be triggered through an API or from the vCenter user interface. The main service receives the request and communicates with collectors over gRPC. We used a separate sidecar collector for each log type, which made the collectors easier to package and reuse across products. Each sidecar runs the script for its source. ESXi, iDRAC, and vCenter provide APIs we could use to collect logs. For microservice logs, our API sent commands to the relevant pods and collected their output. The collectors ran in parallel, so one slow or failed source did not stop the others. Results were placed in separate folders by log type and packaged into one ZIP. We recorded collector failures in the database and omitted failed items from the final bundle, while keeping successful logs. This gave support teams one artifact without making the entire collection depend on every source succeeding.

04 · Dell / Serviceability ~1 min 25 sec

05 · Hardware and performance telemetry

In Serviceability, we collect hardware information from iDRAC and workload performance metrics from vCenter. For the hardware path, a Helm ConfigMap defines the collection intervals. A scheduled cron job notifies Platform Service, which forwards the request to the Node Agent. The Node Agent translates the authentication context for the target iDRAC and then calls its Redfish API. We use Redfish in this workflow to collect processor health, storage and DIMM hardware information, power supply health, fan speeds, temperature sensor readings, and firmware state. Our collection scripts format the results for the Dell backend. For CPU, memory, and VM performance, we use vCenter Cluster Monitor Statistics, or CMS. For example, iDRAC tells us whether a processor is healthy, while vCenter CMS tells us how much CPU the workloads are using.

05 · Dell / Serviceability / Event & Connectivity ~1 min 40 sec

06 · iDRAC events: detection, mapping, and routing

For event and connectivity handling, I’ll use an iDRAC event as an example. The Platform Service received the low-level event and recorded it in a fault list. The Event Manager polled that list for new records, then used a mapping chart to construct a payload. It could include the event ID, message, component, severity, and relevant node, cluster, or hardware-slot context. That context matters because the event needs to be actionable at the right level. We used node, host, and component information to identify duplicates. The manager waited according to the throttling policy, then checked the state before sending another event. Events were routed to vCenter, and also to the Dell backend when the connection was enabled and backend reporting was required. If the backend connection was not enabled, processing stopped at the vCenter side. I worked on the decision logic, the event payload, and the routing conditions.

07 · Dell / NIM ~1 min 40 sec

08 · Firmware upgrade: inventory → compare → apply

The firmware-upgrade flow starts by collecting the node’s hardware inventory and current firmware versions. NIM reads the catalog file carried by the hardware bundle to get target versions. Dell System Upgrade CLI compares the observed inventory with the catalog. If the installed version already meets the target, NIM does not request an upgrade for that component. If an upgrade is needed, NIM uses the Redfish API to notify iDRAC to perform it. My work covered the node installation and upgrade workflow, including the version decision and the Redfish integration with iDRAC.

08 · Dell / NIM impact ~1 min 25 sec

09 · Faster installation and reliable delivery

I also improved how the installation image reached storage. Originally, it was copied from an OVA mounted through iDRAC, taking around two to three hours. I changed NIM to use a file share over the faster network path. NIM can open the share at startup, or an installer or customer can prepare it and pass the file-server details. My change validates the supplied server and checks connectivity to the iDRAC NIC. The workflow selects a high-speed NIC, configures its IP address, and verifies the file-server connection before copying. If validation fails, NIM reports an error and exits. With the file-share path, copying takes about 30 minutes, depending on network speed. Checking connectivity up front lets us catch a network problem before starting a long copy.

09 · Amazon Internship ~1 min 45 sec

10 · AI model evaluation: latency and token metrics

During my internship at Amazon Alexa, I contributed to both the front end and back end of an internal AI model-evaluation tool. A user entered a prompt and selected one of the supported models. Each model had an ID, which the front end sent to the back end; the back end used it to call the corresponding model API and returned the response. We measured latency from prompt submission until the full response completed. We also recorded the token count in the model response. The front end used response data to draw charts, while CloudWatch metrics were grouped by model name and version. The charts used time on the X axis and latency or response-token count on the Y axis. Each point represented one prompt, with a separate line for each model. Users ran one model at a time and compared their results in the charts. This work connected a user workflow, service APIs, model responses, and operational metrics.

Dell · SDD workflow ~1 min

11 · How we use AI in spec-driven development

At Dell, we used spec-driven development to guide AI-assisted work through clear stages. We start with engineering requirements, then turn them into stories with expected behavior and acceptance criteria. During implementation, we use the skill suited to the task and follow the agreed story and specification. Next, review checks the changes against the requirements, followed by unit tests and integration tests. If review or testing finds a gap, we loop back to the relevant stage, refine the requirement, story, or implementation, and run review and tests again. This is an iterative workflow. The specification and skills give the AI useful context, while engineers review the output and validate the final behavior.
