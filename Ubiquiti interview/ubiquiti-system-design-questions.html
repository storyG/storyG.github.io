01
核心系統設計

設計一套支援大量設備的韌體更新服務。

面試官可能會問：從韌體上傳開始，如何建立發布計畫、讓設備取得更新，並確認更新結果？

先記住三個角色

API + 資料庫

接收請求、判斷資格、保存每台設備的更新狀態。

SQS + Worker

排隊處理後端工作；不直接連設備，也不傳韌體檔。

S3 + CloudFront

S3 保存韌體，CloudFront 負責把大型檔案送到設備。

設備更新程式

下載韌體、驗證安全性、安裝，再透過 API 回報結果。

整體流程：依序看這五步

  1. 上傳韌體：CI／管理者先向 Release API 建立版本資料，取得短效上傳網址，再把大型韌體檔直接上傳到私有 S3。系統驗證簽章、摘要值和硬體相容範圍後，才將版本標記為可發布。
  2. 建立 Campaign（發布計畫）：管理者選擇韌體版本、目標產品／硬體、地區或設備群組，並設定開始時間、分批比例、速率上限和停止門檻。資料庫保存這份計畫與目前進度。
  3. 設備取得更新：設備或使用者 App 呼叫更新 API。API 驗證設備身分、目前版本和 Campaign 資格；符合條件才建立一筆更新紀錄，回傳 updateId 和更新資訊。若設備稍後才連線，也可在 check-in 時再次取得尚有效的更新指令。
  4. 下載與安裝：設備依更新資訊從 CloudFront 下載 S3 裡的韌體，不經 Node.js API 傳大檔。設備驗證簽章、摘要值和硬體相容性後才安裝。
  5. 回報與確認：設備在下載、安裝、重開機後等重要階段呼叫狀態 API。完成健康檢查並確認實際版本符合目標後，服務才記為成功；失敗則保存階段和錯誤資訊。

API 流向：同步處理「接收與記錄」

API 先做必要驗證並把工作狀態寫進資料庫，再快速回覆；不在一次 HTTP 請求裡等待韌體下載或安裝完成。

使用者 App／設備要求開始更新
→
Node.js API驗證身分、版本與資格
→
資料庫交易建立 PENDING 更新紀錄 + 待發事件
→
快速回覆202 Accepted + updateId

資料庫交易搭配 Outbox，避免「資料已寫入但訊息沒送進 SQS」的空窗。API 回覆 202 代表已接受工作，不代表設備已完成升級。

SQS 流向：非同步處理「後續工作」

Outbox Relay讀取已提交的待發事件
→
SQS 工作佇列更新派送／狀態事件
→
Worker通知設備、更新彙總或觸發告警
→
資料庫／通知服務保存後續處理結果

SQS 是後端的工作排隊區。Worker 收到工作後執行對應處理，成功才刪除訊息；失敗時讓訊息稍後重試，重試多次仍失敗則送到死信佇列供調查。設備不會把訊息直接送進 SQS，而是呼叫 API。

例如設備回報「安裝成功」時，狀態 API 記下事件並透過 Outbox 送入狀態佇列；Worker 再更新設備狀態、Campaign 統計和告警。SQS 可能重送，因此以 eventId 去重，並用條件式資料庫更新避免舊事件覆蓋新狀態。

資料庫保存什麼？

Release：韌體版本、適用型號、S3 物件位置、摘要值、簽章及發布狀態。
Campaign：目標設備、發布比例、速率、階段、暫停狀態與門檻。
DeviceUpdate：設備 ID、Campaign／Release ID、目前階段、嘗試次數、回報版本及錯誤。

服務放在哪裡？

Node.js API 以容器部署在 ECS，放於私有子網路並跨多個可用區；公開負載平衡器接收 HTTPS 請求。資料庫保存權威狀態，SQS 緩衝背景工作，私有 S3 + CloudFront 派送韌體。

如果 10,000 台設備同時按下更新

API 維持無狀態並水平擴展；入口設定速率限制，過載時回覆 429 和重試時間。API 只快速驗證、建立更新紀錄並回覆，SQS 吸收已接受的背景工作尖峰；Worker 限制並行數以保護資料庫。Campaign 再依比例和每秒更新上限分批放行，設備重試加入退避與隨機延遲。SQS 只能緩衝已進入服務的工作，不能代替 API 入口的容量與流量控制。

面試時可以這樣總結

「我會把更新決策和韌體傳輸分開。CI 將已驗證的韌體放到私有 S3，管理者建立有分批政策的 Campaign。設備透過 Node.js API 取得適用的更新資訊，再從 CloudFront 下載並驗證安裝。API 和資料庫記錄權威狀態；SQS 則讓後端 Worker 非同步派送通知、處理設備回報和更新彙總。這樣大型檔案不會壓垮 API，更新流量也能分批控制。」

連結你的經驗：Dell NIM 是你最直接的設備更新經驗：取得硬體清單、用 catalog 和 Dell System Upgrade CLI 比對版本，再透過 Redfish／iDRAC 執行升級。Campaign、S3／CloudFront 和 SQS 是依這個職缺延伸出的雲端設計方案。
02
安全與完整性

如何從上傳到安裝，全程保護韌體檔案安全？

面試官可能會問：如何確保只有可信任的韌體能發布和安裝，並防止檔案被替換或裝錯機型？

建置身分授權發布者
→
簽署與更新清單版本 · 硬體目標 · 摘要值
→
私有且不可變的儲存發布 ID／物件版本
→
設備端驗證簽章 + 摘要值 + 相容性

建議回答

我會在發布前、下載授權時和設備安裝前設置多道驗證，不依賴單一校驗碼解決所有安全問題。

  • 發布者：只允許受控的 CI/CD 執行角色或授權管理 API 上傳；分離上傳、審核與發布權限，留下稽核紀錄。
  • 韌體檔案：產生不可變的韌體版本 ID 和更新清單，記錄版本、支援的硬體型號／版本、檔案大小、摘要值和簽章。簽章私鑰限制在受控簽章服務或硬體保護的金鑰管理系統。
  • 儲存與下載：S3 儲存桶不得公開；裝置取得短效、限定物件的下載授權。啟用物件版本控制或不可變發布路徑，避免原地覆寫。
  • 設備端：驗證簽章鏈、摘要值、硬體相容性和版本政策，再進入安裝。將安全拒絕原因回報，但不把簽章私鑰放在設備上。
  • 防降版：依產品安全政策拒絕低於最低允許版本的映像；若允許回退，須由經授權的 復原政策 控制。

校驗碼可偵測傳輸損壞，但無法單獨證明檔案來源可信；來源驗證需靠數位簽章和金鑰管理。

連結你的經驗：可連結 NIM 使用韌體目錄比對硬體與韌體版本的經驗；再說明在雲端發布流程會額外加入簽章、權限和稽核層。
03
S3 與 CloudFront · 大型檔案

如何在全球快速且有效率地派送大型韌體檔案？

面試官可能會問：韌體映像檔很大、設備分布全球，如何降低下載時間、源站負載和傳輸成本？

S3 源站私有、具版本管理的韌體檔
→
CloudFront 邊緣節點依不可變發布路徑快取
→
設備短效授權網址

什麼是源站？S3 是資料庫嗎？

不是。源站是 CloudFront 取得檔案的位置；這個例子裡，S3 儲存韌體映像檔等檔案。資料庫保存的是結構化資料，例如版本資訊、發布計畫設定和每台設備的更新狀態。簡單記：S3 存放檔案；資料庫保存結構化資料；CloudFront 快取並派送檔案。

CDN 怎麼運作？

CloudFront 在不同地區設有邊緣快取。設備要求韌體檔時，CloudFront 先找附近節點：若節點已快取該檔（快取命中），直接回傳；若沒有（快取未命中），CloudFront 從 S3 源站取得檔案並存入快取，再回給設備。之後附近設備要同一個檔案，就可能直接從快取下載，不必每次都回 S3。

設備要求下載檔案
→
鄰近的 CloudFront 邊緣節點快取命中：直接提供
快取未命中 ↓
S3 源站從源站取得、快取後提供

韌體通常用包含 韌體版本／版本號 的不可變檔案路徑，避免快取把舊內容誤當成新版本；只有授權設備應取得下載權限。

建議回答

我會將控制平面 API 與檔案傳輸分開。API 負責授權和取得更新資訊，CloudFront 從私有 S3 源站派送韌體映像檔。

  • 使用不可變 韌體版本路徑，例如 產品／型號／版本／檔名，避免同一 快取鍵 對應不同內容。
  • 設備通過資格與發布計畫檢查後，取得短效簽署網址或等效的受限授權；不公開 S3 儲存桶。
  • 設定合適的快取政策、源站存取權限和下載授權期限；大檔案支援斷點續傳或 範圍請求時，設備端可從中斷處繼續。
  • 依 地區 觀察 快取命中率、源站對外傳輸量、下載成功率、吞吐量和耗時；必要時限制單一地區或發布計畫的並行量。
  • 若大量裝置同時更新，分批發布控制器逐步釋出，讓 CDN 快取預熱，並使源站流量隨設備群組逐步增加。

下載速度可能受設備網卡、網際網路服務業者、Wi-Fi 和區域網路影響，因此要區分 CDN 服務效能與裝置端實際下載速度。

連結你的經驗：你的 NIM 檔案共享改善是裝機階段的傳輸最佳化，從約 2–3 小時降到約 30 分鐘，實際時間受網路影響。可用它說明你理解傳輸路徑和效能瓶頸；CloudFront 全球派送則是不同規模的延伸設計。
04
金絲雀測試 · 分階段發布控制

如何設計金絲雀測試、區域分批、暫停與回復舊版？

面試官可能會問：如何避免一個有問題的韌體版本同時影響所有設備？

先用一個簡單例子理解

假設有 10 萬台路由器要更新。不要一次推給全部設備：先在內部測試幾台，再給一小群真實設備（金絲雀測試）；觀察成功率和故障後，才逐批擴大到更多設備與地區。每一批就是一個 發布批次。

設備群組 是一群符合條件的設備，例如同型號、同硬體版本或同一地區。暫停發布 是先停止把更新派給新設備；回復舊版 是另外安排已更新設備回到已知可用版本，前提是設備支援安全回退。

內部／實驗室基本功能測試
→
金絲雀測試設備群組少量且具代表性的設備
→
依地區分批發布逐步增加設備比例
→
大範圍發布依政策控制

建議回答

  1. 建立不可變更的發布計畫，記錄韌體版本、目標設備條件和設備群組、開始時間、每階段上限、觀察時間和停止門檻。
  2. 先發布給內部測試裝置，再選具代表性的金絲雀測試設備，涵蓋主要硬體版本、地區和連線條件。
  3. 每個發布批次設定最大裝置數、最大更新速率和最短觀察時間；下一階段必須等上一階段達標。
  4. 分母使用「已被指定更新且已到觀察時間」符合資格的設備，分開看成功、失敗、處理中和離線，避免離線設備扭曲成功率。
  5. 超過錯誤率、失敗類型或設備健康門檻時，自動暫停；經調查後由授權人員 恢復發布、取消或建立回復舊版計畫。

地區和設備群組讓爆炸半徑可控；每一個狀態轉換都記錄操作者、時間、政策版本與理由。

成功率怎麼算：假設 100 台設備被分到這一批，其中 10 台離線，剩下 90 台已經有足夠時間完成更新；若 85 台成功、5 台失敗，就用這 90 台計算這一批的結果。離線設備先單獨列出，避免把「還沒連線」誤算成更新失敗。

連結你的經驗：你在 NIM 做過單一節點 硬體清單與韌體版本判斷與升級執行。這題可從單台設備更新延伸至設備群組層級的分批發布控制。

設備 API · 離線時的更新處理

設備如何查詢更新？設備離線很久後重新連線時，如何安全取得更新？

面試官可能會問：設備多久向服務查詢一次？如何避免數百萬台設備同時呼叫 API？離線設備重新連線後，如何取得仍適用的更新？

A · 設備查詢可用更新
設備定時詢問服務「我的型號有新版嗎？」
→
服務檢查更新是否適用型號／目前版本／發布批次
→
回覆更新資訊版本、檔案位置、有效期限
→
設備下載並安裝安裝後回報結果
B · 通知設備使用者
設備被排入韌體更新批次
→
建立通知工作AWS SQS 暫存通知工作
→
應用程式／推播／電子郵件「你的設備有更新可用」
→
使用者開啟應用程式應用程式再次向服務確認

設備報到（定時報到）

設備定期向伺服器查詢「有沒有適用的更新？」設備離線也沒關係，下次連線再問即可。這是最容易先實作的方案。

SQS（背景工作佇列）

可把它想成通知工作排隊的收件匣。服務先放入待辦工作，由背景工作處理器逐筆發送通知，避免一次要通知很多人時把系統塞住。

更新清單（更新清單）

更新清單描述目標版本、適用設備和韌體檔案位置；它本身不是韌體檔案。

暫時下載連結

設備確認有權更新後才取得短時間有效的檔案連結；不要把長期有效的下載網址放在電子郵件或推播通知中。

用面試口吻回答

「我會分開處理設備更新和使用者通知。舉例來說，新韌體先進入一批相容路由器的更新計畫。設備定期向服務報到；伺服器確認型號、目前版本和發布批次均符合條件後，回覆更新版本和下載資訊；設備接著下載並安裝韌體，並回報成功或失敗。」

「使用者通知則在設備被排入發布批次後，透過佇列交給通知服務，依帳戶設定送到 應用程式、推播 或 電子郵件。通知只告知有更新和更新內容摘要，不直接附上長效下載權限。使用者打開 應用程式 時，應用程式 再向服務確認更新目前仍適用，然後由設備自己的認證流程取得下載權限。」

「這樣即使使用者沒有看到推播，設備下次報到仍然能取得更新；如果一次有大量設備進入 分批發布，佇列可以讓通知分批發送，避免瞬間流量尖峰。」

06
狀態機 · 冪等處理

訊息或狀態回報重複、延遲時，如何確保更新流程可靠？

面試官可能會問：SQS 可能至少一次投遞；設備也可能重送狀態或遇到網路延遲。如何避免狀態錯亂和重複安裝？

符合資格已指派目標
→
已通知已提供更新清單
→
下載中
→
安裝中
→
成功／失敗

建議回答

  • 定義明確狀態機：符合資格 → 已通知 → 下載中 → 安裝中 → 成功／失敗；只允許合法轉移。
  • 每次更新使用更新 ID（設備 + 發布計畫 + 韌體版本）作為冪等鍵；重複訊息不建立第二個更新工作。
  • 狀態事件帶事件 ID、序號／版本或時間資訊；拒絕舊狀態覆蓋較新的狀態，並設定合理的狀態保留時間。
  • SQS 消費者依照「訊息可能重複送達」的前提設計；資料庫條件更新或版本欄位控制並行寫入，失敗訊息進 死信佇列 並可重放。
  • 設備回報與發布計畫彙總分開處理：原始事件可保留作稽核，聚合狀態由可重建的 背景工作處理器 更新。

狀態以設備回報為事實來源之一，但服務端要區分 更新指令已送達、裝置已開始、安裝成功以及成功後重新報到，不能把「已派送」當成「已更新」。

如果同一個更新指令送來兩次

假設設備 A 被要求更新到韌體版本 R17，API 用設備 ID + 發布計畫 ID + 韌體版本 ID 建立唯一的更新工作。第二次收到相同觸發訊號時，服務端找到原本的更新工作，回傳目前狀態，不另開一筆。資料庫的 唯一性限制或條件式寫入可處理兩個請求幾乎同時到達的情況。

設備端也要再做一次保護：同一個 update ID 若正在下載或安裝，就回報「進行中」；若查到設備目前韌體已是 R17，則回報「已是目標版本」並跳過安裝。執行韌體寫入時每台設備同時只允許一個進行中的更新。完成後重新讀取版本並回報，避免只因收到命令就標記成功。

這樣就算 佇列 重送、使用者連按兩次，或服務逾時後重試，也只會有一筆更新工作。不同發布計畫指向相同韌體版本時，也可以由設備的目前版本與 韌體套件摘要值 判斷是否已完成；若要強制重灌，則需設計明確的修復／強制更新政策，不能默默把它當一般更新。

07
失敗處理 · 回復舊版

金絲雀批次的更新開始失敗時，如何停止發布並復原設備？

面試官可能會問：錯誤率突然上升或新版本讓設備無法正常工作時，控制平面與設備各自應如何處理？

建議回答

  1. 立刻將 發布計畫切換為暫停，停止簽發新的更新清單／下載授權；已下載和已開始安裝的設備要另外觀察，不能假設暫停會中止本機操作。
  2. 依硬體版本、地區、韌體版本、失敗階段和錯誤碼切分指標，確認是否為單一相容性或網路問題。
  3. 保留已發布 韌體檔案 和 發布計畫稽核紀錄；不要覆寫原韌體版本。建立修正版韌體，經過驗證後重新小批 分批發布。
  4. 回復舊版需建立另一個受控發布計畫，將裝置指向已知良好版本；需確認設備的開機載入程式／產品是否支援安全回退或 雙映像區／A-B 韌體映像。
  5. 若設備無法連線或無法啟動，須依產品復原能力設計現場或本地復原流程；雲端服務不能單方面保證失聯設備可回復。

我會把自動暫停 門檻設得保守，並提供人工介入選項、審計紀錄和緊急停止開關。

連結你的經驗：你的 NIM 流程能決定是否需要 韌體升級，Serviceability 則提供診斷記錄檔與事件。可連結「更新決策」與「故障調查」兩端。
08
REST API · 資料模型

韌體版本、發布計畫與設備狀態需要哪些 API 和資料模型？

面試官可能會問：如何讓管理服務建立韌體版本／發布計畫，設備取得更新，且服務可追蹤每台設備狀態？

先用白話理解：三種東西

韌體版本：要發布的韌體版本，例如 Router-X 的版本 2.4.1。
發布計畫：決定把哪個韌體版本發給哪些設備、何時開始、先發多少台。
單台設備更新紀錄（DeviceUpdate）：記錄某台設備在這次發布計畫中目前是待更新、下載中、成功或失敗。

可以把它想成：倉庫裡的韌體版本、配送計畫，以及每台設備的更新進度。同一個韌體版本可以用於不同發布計畫；每台設備也需要各自的更新狀態紀錄。

管理端 API

POST /releases · POST /campaigns · POST /campaigns/{id}/pause · GET /campaigns/{id}

設備端 API

POST /devices/{id}/check-in · POST /updates/{id}/events
設備報到時會詢問「我有沒有適用更新？」；事件 API 回報「我下載／安裝到哪一步」。

韌體版本資料

韌體版本 ID、產品、硬體相容範圍、版本號、更新清單、韌體檔案鍵、摘要值、簽章、發布狀態

發布計畫／設備更新紀錄

目標條件、發布政策、狀態、時間、嘗試次數、最後錯誤、設備回報版本

建議回答

簡單說，管理者用管理端 API 登記韌體並建立發布計畫；設備用設備端 API 詢問自己是否符合更新條件，以及回報進度。兩種入口分開授權：管理端 API 僅供內部管理者／CI 使用，設備端 API 則負責驗證設備身分。設備報到時，服務只回覆對這台設備適用的版本與短效下載權限。

  • 韌體版本中繼資料和發布政策不原地改寫；修改策略時記錄修訂版本，確保能重建當時決策。
  • 發布計畫追蹤總目標、設備群組、速率限制、階段、狀態和暫停原因。
  • 設備更新紀錄追蹤每台設備針對發布計畫／韌體版本的狀態、嘗試次數、時間戳、設備回報版本和錯誤碼。
  • 大量設備事件寫入可經 SQS 批次化；發布計畫彙總使用預先聚合的資料，避免每次都掃描整張資料表。
  • 支援冪等鍵、分頁、API 版本管理、稽核紀錄和速率限制。

資料庫依查詢模式選擇：發布計畫及其關聯查詢複雜、需交易時可選 RDS；以設備 ID 快速查詢狀態、可水平擴展且符合明確資料存取模式時可選 DynamoDB。不要只因為服務名稱熟悉就選資料庫。

09
可觀測性 · SRE

全球分批發布期間，應監控哪些指標並設定哪些告警？

面試官可能會問：如何及早發現更新事故？應觀察哪些設備、發布計畫、CDN 和 API 指標？

發布健康狀態

符合資格／已通知／已下載／已安裝／成功／失敗／離線數量

失敗訊號

依韌體版本、型號、硬體版本、地區與更新階段統計失敗率

派送健康狀態

CDN 快取命中率、源站流量、下載延遲、傳輸量、HTTP 錯誤

服務健康狀態

API 第 95／99 百分位延遲、4xx／5xx、佇列等待時間／深度、背景工作處理器錯誤、資料庫限流

建議回答

我會同時看服務健康和更新成效。CloudWatch 儀表板依發布計畫／韌體版本、型號／硬體版本、地區和更新階段分類；告警不能只看所有設備的整體平均，因為局部相容性問題可能被平均值掩蓋。

  • 服務指標：API 延遲與錯誤率、佇列深度與等待時間、背景工作處理器成功率、資料庫限流，以及 S3／CloudFront 錯誤。
  • 產品指標：符合資格設備數、報到率、下載開始／完成數、安裝成功／失敗數、完成時間，以及離線或停滯設備比例。
  • 安全門檻：單一硬體版本的失敗率、同一錯誤碼突增、金絲雀批次與基準值的差異。
  • 使用結構化記錄、追蹤／關聯 ID 和稽核事件串起發布計畫 → 設備 → 更新嘗試；避免把敏感憑證寫入記錄。
  • 告警連到明確 處理手冊：自動暫停條件、值班人員、查詢維度及 恢復發布／回復舊版 流程。

面試時可補充：我在 Amazon 用 CloudWatch 追蹤延遲與回應 token 數量，在 Dell 的 Serviceability 工作則處理 記錄檔、遙測資料與事件；這些是我在監控與觀測方面的實作基礎。

10
擴展性 · 成本 · 韌性

數百萬台設備同時報到或下載時，如何維持服務並控制 AWS 成本？

面試官可能會問：大型發布計畫啟動後，如何避免 API、佇列、資料庫和源站被流量尖峰壓垮？如何降低成本？

建議回答

  • 避免同步尖峰：設備定期查詢時加入隨機延遲，發布計畫依設備群組／地區分批啟用；API 依設備、地區和發布計畫設定速率限制。
  • 隔離大檔流量：由 CloudFront 快取並派送韌體；API 只回傳更新清單和下載授權，不代理韌體映像檔。
  • 非同步處理：SQS 緩衝設備報到事件和狀態更新的流量尖峰；背景工作處理器可水平擴展，對下游資料庫設定並行處理上限。
  • 資料存取：依設備 ID／發布計畫 ID 設計分割鍵和資料存取模式；預先計算發布計畫彙總，避免儀表板每次查詢都掃描大量設備資料列。
  • 成本控制：觀察 CDN 對外傳輸量、快取命中率、儲存生命週期、佇列與背景工作處理器使用率，以及每次成功更新的成本；保留必要版本，依保留政策清理舊韌體檔案。
  • 韌性：設定熔斷、退避重試、死信佇列、可重放事件、服務降級和發布計畫暫停機制。控制 API 與下載服務分開擴縮並設定告警。

我會先用預期 設備總數、每日報到比例、韌體映像檔大小、發布時間範圍和目標下載完成率，估算每秒請求數、頻寬與儲存，再用壓力測試驗證容量，不憑空指定單一架構數字。

連結你的經驗：可從 NIM 檔案共享傳輸改善談效能瓶頸和網路依賴；再延伸到全球場景中用 CDN、設備群組、隨機延遲和速率限制控制流量與成本。
